It’s become common to hand an agent a code change and let it run the tests. Even one task can take several model calls, so developers looking to cut inference costs are paying attention to how many tokens they send on each call. One example is Code Mode, an experimental feature Anthropic added to Claude Code. Claude Code runs JavaScript written by the model to call several tools. If two tests out of 100 fail, that code can return just the two errors to the model.

At the same price per input token, sending fewer tokens does lower the input cost. There’s no reason to pay for 98 passing test logs I won’t need again. An operations document is different. I may need it for this question and again three turns later. **Over the whole task, is it cheaper to retrieve documents for each question and append them to the conversation, or to keep the documents I expect to reuse at the front of the prompt?**

## How one turn becomes several model calls

If I ask Claude Code to find out why a test failed, the model’s first response might be a request to run `pytest`. Claude Code runs the command, adds the result to the conversation, and calls the model again. The server’s job of processing the input and generating response tokens is called **LLM serving**. The program that assembles the model’s input, runs its tools, and makes the next call is an **agent harness**. Claude Code, Codex CLI, and `pi` are all examples.

The second call includes both the new test logs and the project instructions from the first call. If the two inputs match from the beginning and the server still has the results of processing that shared prefix, it can reuse the work. This is **prompt caching**. The instructions count toward the input token total on both calls, but on the second call they may qualify for the lower cache-read rate.

## Two ways to give an agent access to 408 operations documents

To look up a configuration value, an agent usually needs only a few relevant documents. What happens if it needs the same document again three turns later? I put together 408 synthetic operations documents and asked eight questions per session. Some questions called for a document the agent had seen a few turns earlier. I gave both setups the same questions in the same order and changed how the documents reached the model.

- **Retrieve documents every turn.** For each question, I appended a set of documents retrieved with BM25 to the end of the conversation. Earlier search results stayed in the conversation, so later calls could read them from the cache.
- **Maintain a working set.** At the start of each session, I put documents likely to be reused at the front of the prompt and kept them there for all eight turns. The agent could fetch other documents through tools. I designed the policy for choosing which documents to keep, drawing on the ARC page replacement algorithm, and implemented the search and retrieval tools as an MCP server.

I gave both setups a budget of 1,756 tokens, about 5% of the full document collection. For the working set, that budget capped the documents I could place at the front of the session. For per-turn retrieval, it capped the documents I could append on each turn. Both setups used the model provider’s prompt cache. **I wanted to see how document placement changed the number of tokens written to and read from the cache, and how much that changed the cost of a call.** For each call, I multiplied the ordinary input, cache-write, cache-read, and output token counts by their respective rates for that model and access route at the time of the experiment, then added them up.

## Why did the setup with more input cost less?

I ran the comparison in `pi` once the working set had nearly filled its 5% budget. For each model, I compared 12 pairs of sessions that received the same questions. On the OpenAI model, **the working set used 37.3% more input tokens than per-turn retrieval and cost 19.8% less.** On the Anthropic model, input grew by 6.0% and cost fell by 48.2%.

In the OpenAI experiment, the working set **wrote 124,627 fewer tokens to the cache and read 552,616 more.** On that route, writing one token to the cache cost as much as reading 12.5 tokens from it. The money saved by writing fewer new documents outweighed the cost of reading the same documents again. After including ordinary input and output, the estimated cost was 19.8% lower. Both setups scored 87.5% on the lookup questions, so the lower cost came with no drop in measured accuracy on this task.

Would it make a difference even if the input length barely changed? In Claude Code, I ran the same eight turns with the working set twice in quick succession. The first calls of the two runs differed in length by just 8 input tokens. Yet the number of tokens written to the cache on that first call fell from 28,753 to 6,720. The **estimated cost of the full eight-turn session** fell from $0.3332 to $0.2078, a drop of about 38%. I also repeated the per-turn retrieval session at the same time. Its estimated cost was $0.2649 on both runs.

## Keeping too many documents can get expensive

For a standalone question, I could give the agent all the documents up front, or start it with none and let it find what it needs. For a series of questions, I could put all the documents at the front once and leave them there. If the model can read the same prefix from the cache cheaply, why bother choosing which documents to keep?

In Codex CLI, I ran each of four setups for 12 sessions of 16 turns each. I varied which documents the model saw and whether earlier search results stayed in the conversation. That version of Codex CLI reported ordinary input and cache writes together, so I could compare token counts but couldn’t calculate a separate cost for cache writes.

With all 408 documents up front, the cache-read share was 93.1%, close to the working set’s 91.2%. But the model read 14.89 million tokens from the cache with the full collection and 6.17 million with the working set. Keeping all the documents meant reading **2.4 times as many tokens from the cache**, an extra 8.72 million tokens over the 12 sessions.

Did those extra reads buy better answers? In both setups the agent could access the document containing the answer, using a tool if it was missing from the working set. I excluded the first question in each session because it asked for the current setting but the answer key listed an older value. The agent answered 179 of the remaining 180 questions correctly with all 408 documents up front and all 180 with the working set. For this task, which asked for one setting at a time, keeping every document didn’t yield more correct answers.

I went back to the eight-turn sessions in `pi` to see how the document budget affected cost on the OpenAI model. The earlier comparison used 12 sessions in which the working set had nearly filled its 5% budget. This time I included **all of the first 12 sessions, starting with an empty working set**. The working set could grow between sessions, and its documents stayed fixed within each one. At a 5% budget for both setups, the working set cost 29.6% less than per-turn retrieval. At 2.5% for both, the working set cost **17.8% more** than per-turn retrieval.

## What cutting input saves, and what the experiments can tell us

Providers charge for cached input, so removing text the model would otherwise read on every call lowers the cache-read bill. Skill instructions are one example of text that can stay in context across calls. A study of 40,285 public skills found a median length of 1,414 tokens per instruction file (`SKILL.md`). Loading a skill adds instructions to the prompt and can change which tools the agent uses and how many model calls it takes to finish. File length tells us only part of the cost.

[SkillsBench](https://github.com/benchflow-ai/skillsbench) measured the cost of completing the same tasks with and without skills in two harnesses running Claude Opus 4.7. Task-specific skills raised the mean estimated cost per task by $1.53 in Claude Code and lowered it by $4.62 in OpenHands, an open-source coding agent harness that lets the model edit files and run shell commands.

The totals cover all input and output through the end of each task. For Claude Code, the researchers estimated token counts from session logs that included cache writes and reads. They used LiteLLM to estimate costs.

In my OpenAI experiment, once the working set had nearly filled its 5% budget, the estimated cost per session was 19.8% lower with the working set than with per-turn retrieval. Both setups used the prompt cache, and changing document placement changed which documents the agent read and when it called tools. To isolate caching, I’d compare the cost of processing the same input from scratch with the cost of reading it from cache. To isolate input length, I’d hold the cache conditions steady and vary the length.

In production, **the cost of getting one usable answer** matters. Giving the agent all 408 documents didn’t increase the number of correct answers in this experiment, but every question asked for a single setting. Tasks that require combining information from several documents need a separate evaluation to determine whether giving the agent more material improves accuracy and, if so, whether the gain justifies the extra cost.

## Computing keeps coming back to caching

Computer systems have long cached results to avoid paying for the same computation twice. For the same reason, an LLM reuses the keys and values (KV) from earlier tokens as it generates a response. If the next request starts with the same instructions or documents, the server can reuse the cached KV for that prefix and skip recomputing it.

That difference shows up in API pricing. OpenAI and Anthropic charge less per input token for a cache read than for fresh input. For an agent that needs the same documents across several turns, keeping them at the front of the prompt and reusing the cached prefix can cost less overall than retrieving documents and appending the results on every turn.

In a production service where I used an LLM to generate content, I tuned prompt caching and cut the API cost per item generated by about 70%. That experience gave me a sense of how much cache reuse could matter to the final bill. In the agent experiments, the call logs showed when the savings on cache writes outweighed the cost of reading the same documents again.

Cutting token use is part of an agent’s token economics, and tracing where costs add up across model calls helps you decide what to optimize. If you’re looking to lower your LLM costs, check your token counts and take a look at how well you’re using the prompt cache.
