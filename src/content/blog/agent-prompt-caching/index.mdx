코드 수정부터 테스트까지 에이전트에 맡기는 일이 흔해졌습니다. 작업 하나에도 모델을 여러 번 부르다 보니, 추론 비용을 아끼려고 모델에 보내는 토큰부터 줄이는 시도가 눈에 띕니다. Anthropic이 Claude Code에 추가한 실험 기능인 Code Mode가 한 예입니다. 이 모드에서는 모델이 짠 자바스크립트가 여러 도구를 호출하고 결과를 걸러 냅니다. 가령 테스트 100개 중 두 개가 실패했다면 모델에는 그 두 건의 오류만 돌려줄 수 있습니다.

## 한 턴이 여러 번의 모델 호출로 이어지는 과정

Claude Code에 “테스트가 왜 실패했는지 찾아줘”라고 부탁하면, 모델의 첫 응답은 `pytest`를 실행해 달라는 요청일 수 있습니다. Claude Code가 명령을 실행하고 그 결과를 대화에 더해 모델을 다시 부릅니다. 서버에서 모델이 입력을 처리하고 응답 토큰을 생성하는 일이 **LLM 서빙**입니다. Claude Code, Codex CLI, `pi`처럼 모델에 줄 입력을 구성하고 도구 실행과 다음 호출을 이어 주는 프로그램은 **에이전트 하네스**라고 부릅니다.

두 번째 호출의 입력에는 새로 나온 테스트 로그와 첫 호출에도 있었던 프로젝트 지침이 함께 들어갑니다. 두 호출의 입력이 앞에서부터 일치하고 서버에 그 구간의 계산 결과가 남아 있으면, 서버는 그 결과를 재사용할 수 있습니다. 이것이 **프롬프트 캐싱**입니다. 지침은 두 호출의 입력 토큰 수에 모두 잡히지만, 두 번째에는 더 낮은 캐시 읽기 단가가 적용될 수 있습니다.

## 운영 문서 408개로 비교한 두 가지 배치 방식

운영 문서에서 설정값 하나를 찾을 때는 관련 문서 몇 개면 충분합니다. 그런데 세 턴 뒤에 같은 문서가 또 필요하다면 어떨까요? 저는 가상의 운영 문서 408개를 준비하고 세션마다 질문을 여덟 개씩 던졌습니다. 그중에는 몇 턴 전에 본 문서가 다시 필요한 질문도 있었습니다. 두 방식에 같은 질문을 같은 순서로 주고 문서를 건네는 방법만 바꿨습니다.

- **매 턴 검색하기.** 질문마다 BM25로 찾은 문서 묶음을 대화 끝에 붙였습니다. 이전 검색 결과도 대화에 남아 다음 호출에서 캐시로 읽힐 수 있습니다.
- **작업 집합(working set) 관리하기.** 다시 쓸 만한 문서 묶음을 세션 시작 때 프롬프트 앞에 두고 여덟 턴 동안 고정했습니다. 묶음에 없는 문서는 도구로 가져왔습니다. 남길 문서를 고르는 정책은 페이지 캐시 교체 알고리즘 ARC에서 아이디어를 얻어 직접 설계했고, 검색·조회 도구는 MCP 서버로 구현했습니다.

작업 집합 방식에서는 세션 앞에 둘 문서를, 매 턴 검색 방식에서는 한 턴에 새로 붙일 문서를 각각 1,756토큰으로 제한했습니다. 전체 문서 분량의 약 5%입니다. 두 방식 모두 모델 제공사의 프롬프트 캐시를 씁니다. 제가 확인하고 싶었던 건 **문서 배치를 바꾸면 캐시에 새로 쓰는 양과 다시 읽는 양이 어떻게 달라지고, 그 차이가 호출 비용에 얼마나 영향을 주는지**였습니다. 비용은 호출마다 일반 입력·캐시 쓰기·캐시 읽기·출력 토큰에 실험 당시 모델과 사용 경로의 단가를 각각 곱해 합산했습니다.

## 입력을 더 쓴 쪽이 왜 더 저렴했을까?

하네스 `pi`에서 작업 집합이 5% 예산을 거의 다 채운 상태를 비교했습니다. 모델별로 같은 질문을 받은 세션 12쌍을 집계했더니, OpenAI 모델에서는 **작업 집합을 둔 쪽이 매 턴 검색한 쪽보다 입력을 37.3% 더 쓰고도 비용은 19.8% 낮았습니다.** Anthropic 모델에서도 입력은 6.0% 늘고 비용은 48.2% 줄었습니다.

입력 길이가 거의 같아도 차이가 날까요? Claude Code에서 작업 집합을 두고 같은 여덟 턴을 곧바로 반복했을 때, 두 실행의 첫 호출은 입력 길이가 겨우 8토큰 차이였습니다. 그런데 첫 호출에서 캐시에 새로 쓴 양은 28,753토큰에서 6,720토큰으로 줄었습니다. 그 호출을 포함한 **여덟 턴 전체의 추정 비용**도 0.3332달러에서 0.2078달러로 약 38% 내려갔습니다. 같은 시점에 반복한 매 턴 검색 세션은 두 번 모두 0.2649달러였습니다.

## 문서를 너무 많이 남겨도 비싸져요

독립된 질문에서는 전체 문서를 미리 줄 수도 있고, 문서 없이 시작해 에이전트가 필요한 것만 직접 찾게 할 수도 있습니다. 여러 질문이 이어지는 대화라면 문서를 전부 맨 앞에 한 번 두고 계속 쓰는 방법도 있습니다. 매번 같은 앞부분을 캐시에서 싸게 읽을 수 있다면, 굳이 남길 문서를 골라야 할까요?

Codex CLI에서는 대화에 남길 문서의 양과 이전 검색 결과를 유지하는 방식을 바꿔 가며 입력량을 비교했습니다.

전체 문서를 둔 쪽과 작업 집합을 둔 쪽은 캐시 읽기 비중이 2%포인트도 차이 나지 않았습니다. 그런데 **전체 문서를 둔 쪽이 캐시에서 읽은 양은 2.4배**였습니다. 당시 Codex CLI는 일반 입력과 캐시 쓰기를 한 항목으로 기록했으므로, 이 표에서 확인할 수 있는 건 입력량과 읽기 비중까지입니다.

그만큼 더 읽었으면 답도 더 잘 맞혔을까요? 각 세션의 첫 질문은 현재 설정값을 물었는데 정답표에는 예전 값이 적혀 있어 채점에서 뺐습니다. 남은 180문항에서 문서 408개를 모두 준 쪽은 179개를 맞혔고, 일부만 앞에 두고 필요한 문서를 찾아보게 한 쪽은 180개를 모두 맞혔습니다. 이번처럼 문서에서 설정값 하나를 찾는 작업에서는 전체 문서를 남겨 둬도 정답이 늘지 않았습니다.

읽기 비용이 실제로 쓰기 절감액을 넘어선 사례도 있습니다. `pi`와 OpenAI 모델에서 **작업 집합을 채워 가는 구간**끼리 비교하면, 양쪽의 문서 예산이 5%일 때는 작업 집합 관리가 29.6% 저렴했습니다. 같은 조건에서 예산을 2.5%로 좁히면 작업 집합 관리가 오히려 **17.8% 더 비쌌습니다.**

## 입력 절감의 효과와 실험의 한계

캐시에서 읽을 때도 요금이 붙습니다. 앞의 Codex CLI 실험에서 작업 집합만 남긴 쪽은 전체 문서를 둔 쪽보다 12세션 동안 약 **872만 토큰**을 캐시에서 덜 읽었습니다. 여러 호출에 남는 스킬 지침에도 같은 원리가 적용됩니다. 공개 스킬 40,285개를 조사한 연구에서 지침 파일(`SKILL.md`) 길이의 중앙값은 1,414토큰이었습니다. 다만 파일 길이만 보고는 스킬을 제공했을 때 작업 한 건의 비용이 얼마나 달라질지 알기 어렵습니다.

[SkillsBench](https://github.com/benchflow-ai/skillsbench)는 Claude Code와 OpenHands에 같은 Claude Opus 4.7을 연결해 스킬을 쓸 때와 쓰지 않을 때의 비용을 비교했습니다. OpenHands는 모델이 파일을 편집하고 터미널 명령을 실행할 수 있게 해 주는 오픈소스 코딩 하네스입니다. 작업에 맞는 스킬을 주자 작업당 평균 추정 비용이 Claude Code에서는 1.53달러 올랐고, OpenHands에서는 4.62달러 내렸습니다.

표의 토큰 수는 작업이 끝날 때까지의 입력과 출력을 합한 값입니다. Claude Code의 경우 캐시 쓰기와 읽기를 포함한 세션 로그로 토큰 수를 추정했습니다. 비용은 SkillsBench 연구진이 LiteLLM으로 계산했습니다. 두 열의 차이에는 스킬 지침의 길이뿐 아니라 에이전트가 어떤 도구를 골랐고 모델을 몇 번 불렀는지도 반영됩니다.

OpenAI 모델에 같은 질문을 줬을 때, 전체 문서 분량의 약 5%를 프롬프트 앞에 고정한 쪽은 매번 검색 결과를 뒤에 붙인 쪽보다 세션당 추정 비용이 19.8% 낮았습니다. 두 방식 모두 캐시를 썼고, 문서 배치를 바꾸면서 모델이 어떤 문서를 읽고 언제 도구를 호출하는지도 달라졌습니다. 캐싱으로 아낀 금액만 따져 보려면 똑같은 입력을 처음부터 처리할 때와 캐시에서 다시 읽을 때의 비용을 비교해야 합니다. 입력을 짧게 만든 효과는 캐시 조건을 같게 두고 입력 길이를 바꿔 보면 알 수 있습니다.

서비스에서 궁금한 건 **쓸 수 있는 답변 한 건을 얻는 데 든 비용**입니다. 이번 조회 작업에서는 두 방식 모두 정답 문서에 접근할 수 있었지만, 각 세션의 첫 질문에 대해서는 정답표가 문서의 이전 버전을 가리켰습니다. 이 실험으로 답변 한 건당 비용까지 비교하려면 먼저 정답표를 바로잡고, 각 방식의 총비용을 같은 품질 기준을 통과한 답변 수로 나눠야 합니다.

## 컴퓨팅은 돌고 돌아 캐싱

전통적인 컴퓨팅 시스템에서도 같은 계산을 되풀이하는 시간을 아끼려고 결과를 캐시에 남겼습니다. 그 시간에 같은 장비로 더 많은 요청을 처리할 수 있다면 건당 비용도 내려갑니다. LLM도 다음 토큰을 생성할 때 앞선 토큰의 키와 값(KV)을 캐시에서 꺼내 씁니다. 이 KV 캐시를 GPU 메모리에 얼마나 효율적으로 담느냐에 따라 한꺼번에 처리할 수 있는 요청 수가 달라집니다. 프롬프트 캐싱을 쓰면 다음 요청에서도 앞선 계산을 재사용할 수 있습니다. 두 요청의 입력이 앞에서부터 일치하면 서버는 캐시에 남은 구간을 다시 읽고, 그 구간에는 더 낮은 캐시 읽기 단가가 적용될 수 있습니다.

저는 예전에 LLM으로 콘텐츠를 생성하던 프로덕션 서비스에서 추론 요청 한 건당 비용을 줄이려고 사용 내역을 들여다본 적이 있는데요. 같은 내용이 여러 요청에 반복되는 걸 보면서, 이 부분을 프롬프트 캐시에서 다시 읽으면 얼마나 아낄 수 있을지 궁금했습니다. 이번 글에서는 그때의 질문을 떠올리며 에이전트의 호출 기록을 정리했고, 같은 문서를 여러 번 읽는 동안 어디서 비용을 아꼈는지 여러분과 함께 짚어봤습니다. OpenAI 모델에서 문서를 남겨 둔 쪽이 입력을 37% 더 쓰고도 약 20% 저렴했던 건, 같은 문서를 더 읽는 데 든 비용보다 캐시에 덜 써서 아낀 금액이 컸기 때문입니다.

토큰 이코노믹스를 이야기하는 요즘, 에이전트가 쓰는 토큰을 줄이는 것도 중요하지만 호출마다 어디에 비용이 쌓이는지 알아야 손볼 곳이 보입니다. LLM 비용을 줄이고 싶다면 토큰 수와 함께 프롬프트 캐시도 잘 쓰고 있는지 한번 살펴보세요.
